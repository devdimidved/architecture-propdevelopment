### Требования к безопасности

- **Шифрование канала:** Всё взаимодействие между системами PropDevelopment и платформой партнёра должно осуществляться исключительно по защищённым протоколам (например, HTTPS с использованием TLS 1.2 или выше).
- **Шифрование чувствительных данных:** Персональные данные (такие как биометрические данные для домофона или номера автомобилей) должны храниться в зашифрованном виде в базе данных с использованием алгоритмов AES-256.
- **Управление доступом к API:** Только авторизованные пользователи могут отправлять команды на открытие домофона/шлагбаума.
- **Минимизация данных:** Партнёру должны передаваться только те данные, которые абсолютно необходимы для функционирования сервиса — например ID, необходимые для идентификации доступа.
- **Ограничение скорости запросов (Rate Limiting):** Для предотвращения злоупотреблений и DDoS-атак на API партнёра (и на интеграционный слой PropDevelopment) должны быть настроены лимиты на количество запросов.
- **Логирование действий:** Все запросы к API партнёра, ответы, а также критичные события (например, открытие двери/шлагбаума, попытки несанкционированного доступа) должны подробно логироваться как на стороне PropDevelopment, так и на стороне партнёра. Логи должны содержать информацию для идентификации источника запроса и расследования инцидентов.
- **Мониторинг безопасности:** Необходим постоянный мониторинг интеграции на предмет подозрительной активности и потенциальных инцидентов безопасности.

### Протоколы аутентификации и авторизации

1.  **Аутентификация пользователя в мобильном приложении PropDevelopment:**
    *   Остаётся без изменений: собственник аутентифицируется в мобильном приложении PropDevelopment существующими методами (логин/пароль, возможно, биометрия на устройстве или 2FA, если уже внедрено).

2.  **Аутентификация системы PropDevelopment на платформе партнёра (Backend-to-Backend):**
    *   **OAuth 2.0 (Client Credentials Grant Flow):** Предпочтительный вариант. Система PropDevelopment (серверная часть) получает access token от сервера авторизации партнёра, используя свой client ID и client secret. Этот токен используется для всех последующих API-запросов к ресурсам партнёра. Токены должны быть короткоживущими с механизмом обновления (refresh token).
    *   **API Keys (менее предпочтительно, но возможно):** Если OAuth 2.0 не поддерживается партнёром, может использоваться статичный API-ключ, передавемый в заголовках каждого запроса. Ключ должен быть сложным, уникальным для PropDevelopment, и должна быть предусмотрена процедура его безопасной смены.

3.  **Авторизация запросов:**
    *   После успешной аутентификации системы PropDevelopment на платформе партнёра, каждый запрос должен содержать информацию, позволяющую партнёру авторизовать конкретное действие для конкретного пользователя/объекта.
    *   **На стороне PropDevelopment:** Мобильное приложение PropDevelopment передаёт на свой бэкенд идентификатор аутентифицированного пользователя и запрашиваемое действие (например, открыть домофон). Бэкенд PropDevelopment проверяет, имеет ли данный собственник право на это действие (например, доступ к этому домофону).
    *   **Передача контекста партнёру:** Бэкенд PropDevelopment, обращаясь к API партнёра, передаёт идентификаторы, понятные системе партнёра (например, ID домофона, ID шлагбаума, ID квартиры или собственника.
    *   **На стороне партнёра:** Система партнёра, получив запрос от PropDevelopment, должна проверить, что аутентифицированная система (PropDevelopment) имеет право выполнять запрошенное действие над указанным ресурсом (домофоном, шлагбаумом) от имени косвенно указанного пользователя (через сопоставление с данными, предоставленными PropDevelopment при регистрации объектов/пользователей).


### Взаимодействие между системами предприятия и внешней платформой

1.  **Архитектура взаимодействия (Proxy-модель):**
    *   Мобильное приложение собственника **никогда не обращается напрямую** к API партнёра.
    *   Все запросы от мобильного приложения идут на соответствующий бэкенд-сервис PropDevelopment.
    *   Бэкенд-сервис PropDevelopment выполняют необходимую бизнес-логику, аутентификацию/авторизацию пользователя PropDevelopment, а затем формируют и отправляют запросы к API партнёра.
    *   Ответ от API партнёра возвращается на бэкенд PropDevelopment, который обрабатывает его и передаёт результат в мобильное приложение.
2.  **Потоки данных и управления:**
    *   **Управление доступом (Provisioning):**
        *   PropDevelopment является "мастером" данных о собственниках, квартирах и их правах доступа.
    *   **Выполнение команд (открытие двери/шлагбаума):**
        1.  Собственник в мобильном приложении PropDevelopment нажимает кнопку "Открыть дверь".
        2.  Мобильное приложение отправляет запрос на бэкенд PropDevelopment (указывая, например, ID домофона).
        3.  Бэкенд PropDevelopment аутентифицирует пользователя, проверяет его права на управление этим домофоном.
        4.  Бэкенд PropDevelopment отправляет команду на API партнёра (например, `/doors/{door_id}/open`).
        5.  Система партнёра обрабатывает команду, взаимодействует с физическим устройством.
        6.  Партнёр возвращает результат операции (успех/ошибка) на бэкенд PropDevelopment.
        7.  Бэкенд PropDevelopment передаёт результат в мобильное приложение.
    *   **Получение информации (статус, видеопоток):**
        *   Аналогично выполнению команд, запросы на получение статуса или видеопотока (если он транслируется через API партнёра) идут через бэкенд PropDevelopment.

3.  **Интеграционный слой на стороне PropDevelopment:**
    *   Отдельный интеграционный сервис на стороне PropDevelopment, который инкапсулирует всю логику взаимодействия с API партнёра. Это упрощает управление интеграцией, обновление версий API, мониторинг и применение единых политик безопасности.
